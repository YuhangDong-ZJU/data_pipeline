# GPU 批量外参优化（2026-09-07）

此版本改进 `refine` 的执行效率。各功能仍分步执行；候选写到 work_dir，`apply` 才写回外参。
没有重新运行 FoundationStereo 或 NormalCrafter，也没有处理 wrist depth/normal。

## 实现

- 每个 GPU 使用一个常驻进程，机器人网格只加载和采样一次。不同 GPU 动态领取相机批次。
- 将相机 × 拟合帧的投影、双线性深度采样、像素首样本去重和反向传播批量执行。
  固定形状的 scatter 代替每帧的动态 `unique`/索引操作；迭代内不再逐帧读取 GPU 标量。
- CUDA Graph 捕获完整 Adam 迭代，减少 Python 调度和小 kernel 启动开销。
  不支持图捕获时回退到相同目标的普通批量 CUDA；显存不足时分批重试，并缩小后续批次。
- CPU 预读一批 PNG/Parquet 和机器人点集，与当前 GPU 批次重叠；不预读整个数据集。
- 失败且可观测的默认候选从 2,000 次**继续到总计 6,000 次**。参数、Adam 一阶/二阶动量、
  步数和最佳迭代均保留；续跑相机可跨 episode 合批。原先重跑需要 2,000 + 6,000 次。
- 每 1,000 次原子保存相机级断点，恢复时按相同步数重新合批。
  SHA-256 绑定实际输入字节、初值、内参、帧、机器人采样点和协议版本，防止误用旧状态。

## 质量约束

保留 FP32、机器人网格 25,000 点预算/每 visual 最少 200 点、最多 16 个采样时刻、半分辨率深度、
原可见性规则和训练/候选选择帧划分。不启用 AMP、TF32、自适应降点或提前停止。
每个相机独立求梯度；批量中的其他相机不会改变其损失权重。

候选仍由原标量 `depth_loss` 重算并筛选：选择验证残差 < 0.10 m、不劣于初值 + 0.1 mm，
训练残差不劣于初值，位置变化 ≤ 0.30 m、旋转变化 ≤ 25°；不可观测或失败时保留官方初值。
最终 `check` 的全媒体检查及独立帧几何门槛没有放宽。

GPU 归约次序、矩阵乘法和可捕获 Adam 的浮点计算与原实现并非逐位相同。
测试验证了首样本去重、有效点数、损失与梯度的数值一致性，以及保存/恢复连续优化状态；
实际候选仍需经过质量检查。这里不承诺任意 episode 的每一个指标与旧实现完全相等。

## 实测速度

机器：codex-218，Ubuntu 22.04，RTX 4090；PyTorch 2.5.1 + CUDA 12.4，Python 3.11.11。
GPU 同时承载其他作业。所有测试只读取 `/data2/droid`，输出在独立验证目录，输入 SHA-256 前后一致。

| 测试 | 原实现 | 新实现 | 口径 |
| --- | ---: | ---: | --- |
| 同样的 4 个相机，每个 200 次 | 70.92 s | 2.19 s | 同一批深度、初值、点集和帧；含 GPU 准备及标量验收，不含共用的 CPU 输入准备；本次约 32.4 倍 |
| 4 个相机，每个 2,000 次 | 未在本轮做同条件长跑计时 | 8.38 s | 仅迭代；另有约 4.23 s 准备 |
| 一路困难相机从 2,000 续到 6,000 次 | — | 12.42 s | 仅新增的 4,000 次迭代 |
| 2 卡、4 个真实 episode | — | 38.86 s | 生产调度路径，含启动、读取、优化、续跑、断点及候选保存 |
| 1 卡、12 个真实 episode / 24 相机 | — | 70.34 s | 自动批量 9 个相机；含启动、读取、2,000 次默认拟合及一路 6,000 次续跑，12 个候选全部生成 |

`nvidia-smi pmon` 按本任务进程区分其他作业：12-episode 测试中，本任务 PID 2041800 的
**49 个非缺失 SM 活动采样**中位数为 77%，最大 99%。两卡试跑的两个进程对应中位数 82% / 80.5%。
这些是驱动报告的活动采样，不能当作 H100 算力效率或完整运行期间持续 99% 的证明。
启动、输入准备及末尾任务不足一批时会有空隙；共享显卡也会影响时间。

对方 Debian 12 / 8 × H100 没有远程连接，因此没有实测该机器的吞吐量，也不沿用旧实现的全量耗时估算。
生产运行会自动记录各卡、各批次和本次运行总耗时，可据实计算剩余时间。
批量 refine 的速度不等于全流程速度：全部视频解码、元数据重建和最终几何审计仍需独立耗时。

## 与旧候选的独立质量比较

复用此前锁定的每 episode 24 个额外评估帧，排除全部 16 个拟合/候选选择时刻；
使用相同深度、内参、机器人模型、workspace 和 PointWorld 指标定义。
两组都通过相对 DROID 初值的几何门槛。表中的深度是按机器人点数加权的 L1，**不是相机位姿真值误差**。

| Episode | 旧 → 新深度 L1 | 旧 → 新 F1@5 mm | 旧 → 新 F1@20 mm |
| --- | --- | --- | --- |
| 0：强制本地重拟合作为数值对照 | 7.048 → 7.061 cm | 51.542 → 50.834% | 68.715 → 68.686% |
| 9：PointWorld 未覆盖 | 5.893 → 5.897 cm | 63.863 → 63.955% | 74.739 → 74.790% |

结果接近，但并非所有指标都提高：episode 0 的 5 mm F1 下降约 0.71 个百分点。
正式流程中 episode 0 属于 PointWorld 重合部分，直接复用发布外参，根本不会走这一重拟合路径；
其发布外参在相同输入上的 F1@5 mm 仍为 58.893%。episode 9 的外部相机 2 在两种实现中均需 6,000 次预算。
不使用这些额外评估帧反向调参。两个样例不能替代完整数据的独立 `check`。

## 命令、监控和恢复

对方先按 [逐步文档](STEP_BY_STEP.md) 更新仓库并完成前面的独立步骤。
到 4b 时执行：

```bash
bash recam_refine/run_step.sh refine "$RECAM_ROOT" "$RECAM_WORK" \
  --devices 0,1,2,3,4,5,6,7 --gpu-batch-size 0
```

`0` 按可用显存选择，最多每卡 32 个相机。明确设置 `--gpu-batch-size 32` 也受显存回退保护。
默认即可运行。`--workers` 不控制 GPU 并发；它用于其他步骤的 CPU/I/O 进程。

- `calibration_workers.json`：设备、启动时可用显存和批量。
- `calibration_performance.jsonl`：每批 PID、耗时、相机数、续跑数、峰值张量显存和当前批量上限。
- `calibration_timing.json`：本次运行完成数、总时间与失败数。
- `calibration_state/`：绑定输入的 Adam 断点，保留在数据集外。
- `calibration_failures.json`：运行错误；优化不被接收另记入候选和保留初值报告。

中断后重新运行原命令。可以调整 GPU 列表及批量；不能更换初值、深度、迭代预算或算法版本后继续旧断点。
旧 work_dir 保持 reference 后端；新 work_dir 默认 batched，不会悄悄混用。
